# Evidence ledger and attribution

## Source hierarchy

1. Canonical LeetCode problem page: number, title, difficulty, API, constraints and examples.
2. Official platform behavior or documentation when a language/runtime detail matters.
3. Independent references only for cross-checking an explanation; do not copy their wording or code.
4. Locally executed tests and browser reports for claims about this repository.

The problem page is the authority for the contract. An editorial, blog or discussion is not a substitute.

## Evidence JSON

Keep a compact machine-readable record with:
- problem number, official URL, exact title, difficulty and verification date;
- only the constraints that affect the algorithm;
- derived invariant, recurrence or data-structure properties;
- correctness argument summary;
- complexity assumptions;
- tests and reference method;
- explicit input-mutation behavior.

Each claim should be tagged as source fact, derived, or locally tested. A test validates only the implementation and tested domain; it does not prove a universal theorem. A proof supports correctness under stated assumptions; it does not prove code was executed.

## Attribution and copyright

Write a fresh short summary. Do not paste the full problem statement, official editorial, user discussion, proprietary hints or premium content. Do not reproduce third-party diagrams or screenshots. Link the original problem and name external references when their factual insight materially informs the article.

Do not add unsupported acceptance rates, company-frequency claims, runtime percentiles, popularity rankings or "optimal" claims. If a number is not directly verified and relevant, omit it.

## Cross-check before release

Compare the problem title, number, difficulty, constraints, example semantics and method signature with the official page. Ensure the article, tests, code and SVGs all use the same input. Record any deliberate simplification.
